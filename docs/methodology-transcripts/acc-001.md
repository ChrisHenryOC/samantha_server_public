## 1. Input prompt

Given to the assistant as the authoring task. Quoted as delivered.

> **Task.** Author a deterministic rule encoding the following SOP
> fragment from `knowledge_base/sops/accessioning.md` § 3.1:
>
> > "If the order is missing the patient name, hold the order in
> > `MISSING_INFO_HOLD` and request the name. Do not proceed."
>
> **Inputs available.**
>
> - The 9-primitive vocabulary (`IsNull`, `Equals`, `ThresholdGTE`,
>   `ThresholdLTE`, `InEnum`, `Contains`, `BooleanAnd`, `BooleanOr`,
>   `Not`) with the null-discipline contract.
> - The dispatch contract (`step`, `applies_at`, `event_type`).
> - Field shapes on `Order` (see `samantha_server/models/context.py`).
> - Outcome verb-prefix conventions
>   (`docs/rules/conventions.md`).
> - Inventory entry for ACC-001 in `docs/rule-breakdown/inventory.md`
>   (covering scenarios SC-003, SC-004, SC-006, SC-008, …).
>
> **Output required.** A YAML file at
> `samantha_server/rules/specs/ACC-001.yaml` whose `RuleSpec` round-trips
> via the loader and routes the covering scenarios to
> `MISSING_INFO_HOLD` with `applied_rules == ["ACC-001"]`.

## 2. Assistant transcript

### 2.1 Reasoning — fragment classification

The SOP sentence has one trigger condition (*missing patient name*) and
one decision (*hold the order*). No numeric tolerances, no
cross-cutting concerns, no test-conditional branches. Per the
methodology § 4 step 2 "name the dominant case", the trigger is a pure
absence check on a single field.

### 2.2 Tool call — read `Order` to confirm field name and shape

```text
Read samantha_server/models/context.py
```

Result (excerpt):

```python
class Order(BaseModel):
    model_config = ConfigDict(frozen=True, ...)
    order_id: str
    patient_name: str | None
    patient_sex: Literal["M", "F", ...] | None
    ...
```

`patient_name: str | None` — the order-level scalar carries the
*missing* signal as `None`. No `event.<key>` indirection needed.

### 2.3 Tool call — primitive selection

The catalog turn produced this single-line decision:

```text
SelectPrimitive("IsNull", field="patient_name")
```

Justification, recorded in the session log:

- **`IsNull`** is the only primitive that asserts absence
  (methodology § 1, null-discipline paragraph). Every other primitive
  fails-closed on `None`, so `Equals(patient_name, None)` would also
  fire, but `IsNull` is the canonical form and matches the
  categorization table verbatim.
- No `Not(...)` wrapper is needed; `IsNull` already names the
  dominant (failure) case.

### 2.4 Tool call — dispatcher fields

```text
SetDispatch(step="ACCESSIONING", applies_at=None, event_type="order_received")
```

- `step="ACCESSIONING"` from the SOP section (`accessioning.md` § 3.1).
- `applies_at=None` because non-IHC rules carry `null` here per
  methodology § 2.
- `event_type="order_received"` because the order body is what carries
  `patient_name`; the `order_received` event is the only event whose
  payload presents the order shape pre-validation.

### 2.5 Tool call — action and severity

```text
SetAction(
  transition="MISSING_INFO_HOLD",
  severity="HOLD",
  outcome="held_missing_patient_name",
)
```

- `severity="HOLD"` from the SOP verb "hold the order".
- `transition="MISSING_INFO_HOLD"` matches the existing accessioning
  state table; verified against
  `samantha_server/models/context.py:VALID_STATES`.
- `outcome="held_missing_patient_name"` follows the `held_*` prefix
  for `HOLD` severity (`docs/rules/conventions.md` § "outcome
  verb-prefix convention").

### 2.6 Emitted YAML

```yaml
rule_id: ACC-001
step: ACCESSIONING
applies_at: null
event_type: order_received
severity: HOLD
priority: null
when:
  is_null:
    field: patient_name
action:
  transition: MISSING_INFO_HOLD
  set_flags: []
  clear_flags: []
  outcome: held_missing_patient_name
  panel: null
  branch: null
source: knowledge_base/sops/accessioning.md#3.1
```

### 2.7 Validation pass

- `RuleSpec.model_validate(yaml.safe_load(...))` produced a frozen spec
  with `when` resolved to `IsNull(field='patient_name')`.
- Engine smoke against the four covering scenarios in
  `tests/fixtures/scenarios/rule_coverage/` confirmed `ACC-001`
  appears in `applied_rules` for every scenario:
  - `sc-003.json` — only ACC-001 fires; routes to `MISSING_INFO_HOLD`.
  - `sc-004.json` — ACC-001 + ACC-007 (missing billing); routes to
    `MISSING_INFO_HOLD` (HOLD beats PROCEED).
  - `sc-006.json` — ACC-001 + ACC-002 (missing sex); routes to
    `MISSING_INFO_HOLD`.
  - `sc-008.json` — ACC-001 + ACC-003 (anatomic site rejected);
    routes to `DO_NOT_PROCESS` (REJECT beats HOLD).
- The emitted YAML is structurally identical to the canonical
  `samantha_server/rules/specs/ACC-001.yaml` (same primitive type, same
  field literal, same dispatcher fields, same action shape).

## 3. Annotations

### 3.1 What worked

- **The dominant-case heuristic killed all wrapper temptation.** The
  predicate landed as `IsNull('patient_name')` on the first pass — no
  `Not(NotNull(...))` and no `Equals(field, None)` candidates entered
  the tool stream. The methodology § 4 "name the dominant case" line
  is doing real work for trivial rules: the decision was
  one-and-done.
- **The conventions table removed the outcome-naming wobble.**
  `held_missing_patient_name` was the only candidate consistent with
  the `HOLD → held_*` row in `docs/rules/conventions.md`. Without that
  table the assistant would have produced `missing_patient_name`,
  `hold_for_name`, or some near-miss that the corpus-smoke test would
  later flag.
- **`event_type` was unambiguous because of methodology § 2.** The
  rule reads order-level `patient_name`, but the dispatcher key is
  still the *event* the rule binds to, not the field's namespace.
  Methodology § 2's "the kernel dispatches on this field to keep
  predicates from accidentally firing on the wrong event shape"
  pointed at `order_received` immediately.

### 3.2 What required correction

- **Initial severity drift toward `REJECT`.** The first pass at the
  task synopsis read "missing → REJECT" (a colloquial paraphrase that
  shows up in some inventory shorthand). The SOP fragment quoted in
  full says "hold the order … and request the name" — that's
  recoverable, so the correct verdict is `HOLD`, not `REJECT`. The
  conventions table made the disagreement visible: a `REJECT` outcome
  would have to be `rejected_*`, but no `rejected_missing_patient_*`
  exists in the corpus, and the inventory's "covering scenarios"
  column shows the canonical scenarios route to `MISSING_INFO_HOLD`,
  not `DO_NOT_PROCESS`. The correction took one re-read of the SOP
  section.
- **Brief detour on `Equals(patient_name, None)`.** The primitive
  catalog allows `Equals` against `None` (returns true on a null
  field, per the spec text). The methodology § 1 null-discipline
  paragraph is what redirected the choice — `IsNull` is the **only**
  way to assert absence in the corpus, even when other primitives
  could be coerced into the same answer. The session lost ~30 seconds
  here; documenting "use `IsNull` even when `Equals(field, None)`
  would also fire" as the explicit rule (already in § 1) prevented a
  wider wobble.

### 3.3 What surprised

- **The dispatcher fields cost more thought than the predicate.**
  Picking `IsNull('patient_name')` was the cheap step. Justifying
  `event_type="order_received"` (rather than, say, leaving it null on
  the assumption that the step gate would do the work) required a
  re-read of methodology § 2 plus the
  [`decision-gate.md` collision-risk
  examples](../rule-breakdown/decision-gate.md#dispatch-contract).
  For the trivial tier the predicate is the easy part — the
  *dispatch* is where the methodology earns its keep.
- **The `priority: null` requirement is non-obvious from a single
  rule.** ACC-001 is severity-based; `priority` only applies to
  non-ACCESSIONING phases. The Pydantic schema accepts `priority:
  null` but the *requirement* that ACCESSIONING rules carry the key
  explicitly (rather than omitting it) is enforced by `extra="forbid"`
  in the wrong direction — it's the **schema-required** key that
  forces the `null`. A first-time author would expect to omit
  `priority` entirely; only the round-trip test makes the omission
  fail.
- **The covering scenarios disagree on terminal state, but ACC-001
  fires in all of them.** SC-003 isolates ACC-001 and lands in
  `MISSING_INFO_HOLD`; SC-008 has ACC-001 *and* ACC-003 firing, and
  the engine picks `DO_NOT_PROCESS` because REJECT outranks HOLD. The
  rule's correctness is "does ACC-001 appear in `applied_rules`?",
  not "does the scenario terminate at `MISSING_INFO_HOLD`?". The
  severity hierarchy is the kernel's job, not the rule author's —
  another reinforcement of the dispatch-contract / action-handler
  split in methodology §§ 2 and 7. A novice author could easily
  mis-read SC-008 as a counterexample to the rule and start hunting
  for a guard predicate; the receipt format is what makes "ACC-001
  fired, but ACC-003 won the verdict" auditable.
